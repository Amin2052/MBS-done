## 3. Database changes

| Object | Purpose |
|---|---|
| `platform.tenants` | One row per business; slug is the URL handle |
| `platform.users` | Global identity (a person may work for two businesses) |
| `platform.user_by_email(text)` | SECURITY DEFINER lookup; the runtime role has no table grants |
| `tenant.memberships` | (tenant, user, role, permissions) |
| `tenant.sessions` | Opaque token hashes, expiry, revocation |
| `tenant.org_settings` | Business profile, BDT, Asia/Dhaka, digit preference, fiscal year |
| `tenant.audit_log` | Append-only, no UPDATE/DELETE policy **and** no privilege |
| `tenant.counters` | Gapless per-series numbering, locked with `FOR UPDATE` |

Roles: `mbs_migrator` (applies migrations) and `app_runtime` (the application; NOLOGIN,
NOINHERIT, not a superuser, no BYPASSRLS, owns nothing).

## 7. Security findings

- **Two independent layers** ended up protecting `audit_log`: the missing UPDATE policy
  *and* the missing UPDATE privilege. The privilege layer fired first (`42501`), which is
  the stronger outcome — a policy mistake alone would not have opened the log.
- Identity had to be global (one person, two businesses) but scoped away from the runtime
  role: the only path is a `SECURITY DEFINER` function with a pinned `search_path`.
  Browsing every user in the system is therefore not expressible with the app's credentials.
- Policies are generated in one loop, so a new tenant table is one array entry away — and
  the static checker fails the build if that entry is forgotten.

## 9. Known limitations

- PGlite is a single connection: concurrency through a real pool is still unproven and
  remains `blocked` (needs Docker or a managed Postgres).
- `check-rls.mjs` understands `CREATE TABLE` and the generated policy loop; it does not yet
  parse `ALTER TABLE ... ADD COLUMN tenant_id`, which will matter when tables gain columns.
- No migration runner (ordering, checksums, applied ledger) yet — files are applied in
  filename order by the verifier; the runner lands with the API in M4.
- ICU `bn` collation is not decided yet.

## 10. Risks

R2 (float money) is now closed at the schema level: the checker fails the build on `REAL`.
R6 (tenant isolation) has a verified database half; the API/UI half is M4 work.

## 11. Rollback

Migrations are additive and not yet applied to any real database; dropping the schemas is
safe in a development environment.

## 12. Prerequisites for M4

- Session/auth wiring on top of these tables.
- The migration runner with checksums before any shared environment exists.
- A decision recorded for the ICU `bn` collation.
