# M06 — Second-factor sign-in: TOTP and recovery codes

Date: 2026-11-21 · Status: **done-verified** for the sign-in path — enrolment, verification,
recovery codes and the bilingual screen are built and tested; passkeys, a session list and
self-service reset remain open (listed below)

## 1. Completed work

**Owner and manager sign-in is now two-stage** (`apps/api/src/auth.ts`, `mfa.ts`,
`session.ts`, ADR-0017)

- A correct password for an owner or manager returns a challenge, never a cookie. An account
  with no confirmed factor is sent to enrolment instead, so there is no skipped state.
- The challenge is an opaque 256-bit token stored only as sha256, bound to the business the
  password step chose. It expires in five minutes, is spent by one success, is replaced by
  any newer challenge for the same user, and dies after five wrong codes.
- Codes are checked in Node (`packages/domain/src/auth/totp.ts`): RFC 6238, SHA-1, 6 digits,
  30 seconds, ±1 step, 160-bit secret, replay refused by last accepted step.
- Employees and accountants keep the single-stage sign-in; the factor is mandatory only for
  the roles that can move money and edit statutory details.

**Enrolment in the sign-in flow**

- The server generates the secret, seals it, returns it once with an `otpauth://` URI and a
  group-of-four display form, and activates the factor only when the first code verifies.
- Ten recovery codes (12 characters, no look-alikes, ≈59 bits each) are generated then,
  returned once, stored as sha256 and spendable once.
- A pending secret is rotated on every enrolment challenge, so an abandoned or observed
  pending secret cannot be used later.

**Recovery**

- A recovery code signs in exactly once and is audited as `strength: recovery`.
- The screen offers "use a recovery code instead" and switches the field to text entry.

**Secrets at rest**

- TOTP secrets are sealed with AES-256-GCM under `MBS_MFA_KEY` (32 bytes, outside the
  database). The API refuses the documented development key when `NODE_ENV=production`.
- The `otpauth` secret is never returned again after enrolment, and never in a log.

**Throttling**

- A wrong code spends one of five attempts and also registers a login failure for the
  address, so the second factor cannot be ground down by reopening challenges.
- Migration `0004` gives the throttle the caller's clock: one rule, one clock.

**Bangla and English**

- 26 new messages per catalog (111 total), sign-in headings, hints, the setup key, the
  recovery-code list and every error state translated; the gate checks parity and
  placeholders.

**Development**

- `npm run mfa:code -- <secret>` prints the current code, so the demo and support can check
  the algorithm without a phone.
- The demo owner arrives enrolled with a printed demo secret; the manager and the
  multi-business owner reach the enrolment screen, which needs no app for the demo.

## 3. Database changes

`0003_mfa.sql` adds three `platform` tables — `mfa_credentials` (sealed secret, confirmed
flag, last accepted step), `mfa_recovery_codes` (sha256, `used_at`), `mfa_challenges`
(sha256 token, bound business, purpose, attempts, expiry) — and ten SECURITY DEFINER
functions. No tenant table and no RLS policy changes; `app_runtime` gets zero table
privileges on all three.

`0004_login_clock.sql` replaces `platform.login_record_failure(text, integer, integer)` with
a four-argument version that takes the instant, so the API and the database never disagree
about whether an address is locked. The old signature is dropped.

## 4. API changes

- `POST /api/v1/auth/login` — `200` now also returns `{ mfa: { status, challenge_token,
  expires_at, enrollment? } }` and no cookie when a factor is required.
- `POST /api/v1/auth/mfa/verify` — `{ challenge_token, code }` → session cookie.
- `POST /api/v1/auth/mfa/enroll` — `{ challenge_token, code }` → session cookie plus
  `recovery_codes` (once).
- `openapi.json` gained both routes, their request bodies, `401` and the cookie header.

## 7. Security findings

- **Nothing to steal before the password.** A missing account and a wrong password stay
  indistinguishable and fast; the factor is only mentioned after the password verifies.
- **The challenge token is not a credential on its own.** Hashed at rest, single use,
  five-minute life, one live challenge per user, five-code ceiling, and it dies with a new
  sign-in attempt.
- **Replay is refused.** A code is accepted once per step per credential, so an observed
  code is not enough within its window.
- **Recovery codes are not grep-able.** Only sha256 of the dense form is stored; the plain
  codes exist in one response.
- **Database-only access is not enough** to forge codes: the secret is AES-GCM ciphertext
  under a key outside the database.
- **Enrolment cannot be hijacked** by an old pending secret, and the tenant and role a
  challenge belongs to are re-proved at code time.
- **The tenancy gate stayed strict.** `mfa_challenges` deliberately names its column
  `bound_tenant_id`; had it been `tenant_id`, `tools/check-rls.mjs` would (correctly) demand
  RLS on a table that must never be reachable through tenant context.

## 9. Known limitations

- **Codes are phishable in real time**; passkeys/WebAuthn are the planned follow-up and are
  additive to this design.
- **No self-service reset.** An owner with no phone and no recovery codes needs another
  owner or support; the support runbook is not written yet.
- **No session list / revoke-all**; logout still revokes only the current session.
- **One factor per account**, shared across businesses: the person is the subject, so a
  second factor is not per-business.
- **No QR image.** The setup key and the `otpauth://` URI are shown; apps accept manual
  entry, and no QR dependency was added.
- **No DOM tests**; the screen is covered by type-checking, the build and the client tests.
- **`MBS_MFA_KEY` is an operational secret.** It is not in this public repository, so a
  deployment must set it; losing it invalidates every enrolled factor.

## 10. Risks

R7 (session theft) drops for privileged accounts: a stolen password no longer signs in
alone. R6 (tenant isolation) is unchanged and now includes the challenge's bound business.
New risk: losing `MBS_MFA_KEY` locks every enrolled owner out — needs the disaster-recovery
runbook before real onboarding.

## 11. Rollback

Drop `0003` and `0004` (or restore the three-argument `login_record_failure`), remove the two
routes and set the owner/manager branch in `auth.login` back to immediate session creation;
the portal then shows the password-only screen again. Enrolled accounts simply stop being
asked. No tenant data is touched.
