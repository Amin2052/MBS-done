# M07 — Owner portal shell: navigation, routing and a real-data dashboard

Date: 2026-11-22 · Status: **done-verified** for the shell, the router and the dashboard —
every number on the screen comes from a tenant-scoped endpoint, the gate is green, and the
remaining owner screens are listed below

## 1. Completed work

**Routing (ADR-0018, which replaces ADR-0016's “no router yet” clause)**

- A fixed two-route table: `/` is the dashboard, `/profile` is the business profile.
  Unknown paths render a translated not-found screen inside the shell.
- `lib/router.ts` is ~90 lines with no dependency: trailing-slash normalisation, no case
  folding, `popstate` for back/forward, and `pushState` navigation.
- Links stay real `<a href>` elements. A plain left click on a same-origin http(s) link is
  taken over; modifier keys, middle clicks, external hosts, `javascript:` and `data:` are
  left to the browser. The decision is a pure, tested function.
- Deep links and refresh already work because `apps/api/src/static.ts` answers unknown
  extension-less paths with `index.html`; no server change was needed.

**Shell (`AppShell.tsx`)**

- Sidebar navigation with Dashboard and Business profile, inline SVG icons and
  `aria-current="page"` on the active item. The list is only screens that exist and pass
  tests — not the legacy module list.
- The existing topbar keeps language, signed-in identity, role chip and sign-out.
- At ≤ 860 px the sidebar becomes a horizontal strip under the topbar and the page uses
  one column; the page width grows to 1040 px on desktop.

**Dashboard (`DashboardScreen.tsx`, `GET /api/v1/dashboard`)**

- One authenticated endpoint, run through `withTenant`, returns: the business profile
  (name, slug, legal name, BIN, currency, numbering system, fiscal year, VAT flag), active
  team counts and a per-role breakdown, the last ten append-only audit entries, and the
  current session's role and expiry.
- The screen renders business details, a team card with the total and role rows, a session
  card, and an activity list with translated known actions (`auth.login`, `auth.logout`,
  `auth.mfa_enroll`, `org.update`) and a generic translated fallback for anything else.
- Loading, error/retry, and empty-activity states are implemented; a 401 returns the user
  to sign-in through the existing `onSessionLost` path.
- **No invented metrics.** Sales, stock, receivables and money widgets are not shown
  because their modules do not exist yet (spec 7A).

**i18n**

- 30 new message ids per catalog (141 total): dashboard labels, activity labels, the
  navigation label and the not-found screen. Bangla and English pass the parity and
  placeholder gate; all numbers and dates use the business's digit setting and
  `Asia/Dhaka`.

**Tests**

- Five router tests: route resolution, trailing slashes, case sensitivity, click
  interception rules, and a check that every menu entry resolves to a screen.
- One API test over real HTTP and real PostgreSQL (PGlite): the dashboard returns the
  session's business, rejects a cookie-less request, is readable by an employee, and a
  cookie for business B never sees business A's name or team count.
- The API and MFA fixtures now derive their clocks from `Date.now()` instead of a pinned
  past instant. `tenant.sessions.created_at` defaults to the database's `now()`, so the
  pinned fixture made `expires_at > created_at` fail once the calendar rolled over. This
  is a test-fixture fix, not a relaxation: the expiry assertion is unchanged.

## 7. Security findings

- The dashboard is scoped twice: by the transaction's RLS policy and by an explicit
  `tenant_id` predicate. The business id comes from the resolved session, never the
  request; there is no parameter a browser could alter.
- Activity rows expose only action, entity and time. The audit log's `before`/`after`
  snapshots are not returned, so the dashboard cannot become a side channel for profile
  history.
- The session card shows only the caller's own address, role and expiry.
- The router refuses to intercept `javascript:`, `data:`, protocol-relative and external
  links; those reach the browser's own handler. No URL is ever written into `innerHTML`.
- **Navigation is not a control.** Every API route still resolves the session and checks
  the role; hiding a menu item grants nothing and showing one grants nothing.
- The dashboard's three queries run inside one tenant transaction; no query is issued
  outside it.

## 9. Known limitations

- The dashboard has no sales/inventory/money widgets because those modules do not exist;
  it shows profile, team and activity only.
- Team counts are active memberships; pending invitations are not counted (no invitation
  flow yet).
- Activity is the last ten entries with no filter or pagination; the full audit screen is
  a later module.
- No `document.title` per screen, no breadcrumbs, no route-level code splitting and no
  session list (revoke-all is still the next auth unit).
- Navigation is static rather than permission-derived; the permission catalogue and
  invitation flow are M4/M5 work.

## 10. Risks

- **R6 (tenant isolation)** is unchanged and extended: the dashboard adds one more
  tenant-scoped read, tested across two businesses and a cookie-less request.
- A dashboard load is three small indexed queries. At the 3.3 load model this is
  negligible; it is not yet measured under load (M14).
- The router is deliberately minimal; when nested layouts or public pages arrive, a
  framework may be justified — ADR-0018 records that it can be swapped behind the same
  screen props.

## 11. Rollback

Remove the `GET /api/v1/dashboard` route and its OpenAPI entry; delete
`DashboardScreen.tsx`, `router.ts`, `nav.ts` and `NotFoundScreen.tsx`; return `App.tsx`
to rendering `ProfileScreen` directly. No database object is touched, so rollback is a
code revert only.
