# ADR-0007 — Background jobs and queues

**Status:** Accepted · **Date:** 2026-11-21 · **Class:** D1 · **Reversibility:** high
(jobs are declared as named tasks with JSON payloads)

## Context

Long-running work that must not sit in a request: PDF batches, invoice regeneration,
ETL rehearsals, backups, restore verification, metering rollups, email/SMS sending,
webhook retries, orphaned-file reconciliation. Spec 5.6 requires a **tenant-aware** job
queue where tenant context is set per job transaction.

## Options considered

| Option | Assessment |
|---|---|
| Redis + BullMQ | Fast, mature, but adds a stateful service to operate, back up and secure. |
| Cloud queue (SQS etc.) | Fine, but couples the deployment to a cloud provider before M15 decides one. |
| **PostgreSQL-backed queue** (`graphile-worker` style) | Uses the database we already run and back up; `FOR UPDATE SKIP LOCKED` gives correct concurrency; jobs are transactional with the data they touch; no extra service. |

## Decision

A PostgreSQL-backed queue table `platform.jobs` with `SELECT … FOR UPDATE SKIP LOCKED`:

```sql
create table platform.jobs (
  id            bigserial primary key,
  task          text not null,
  payload       jsonb not null default '{}'::jsonb,
  tenant_id     text,              -- null for platform tasks
  run_at        timestamptz not null default now(),
  attempts      int not null default 0,
  max_attempts  int not null default 5,
  locked_by     text,
  locked_at     timestamptz,
  last_error    text,
  created_at    timestamptz not null default now()
);
```

Worker rules:
- Each job runs inside `withTenant(tenant_id, …)` so RLS applies exactly as in requests.
- Retries use exponential backoff; after `max_attempts` the job is parked for inspection,
  never silently dropped.
- Tasks are idempotent by contract (ETL and PDF regeneration must both be re-runnable).
- A job that touches no tenant (metering) runs as the platform role, which has no grants
  on tenant tables.

## Consequences

- Backup/restore covers the queue automatically; no separate Redis snapshot problem.
- Throughput is bounded by PostgreSQL, which is ample for < 200 businesses.
- The worker is a separate process (`apps/api` worker entrypoint), deployable alongside
  the API but scalable independently.
